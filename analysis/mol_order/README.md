# MOL files instead of SMILES: primitive first-atom encoding

Generated by `python -m experiments.run_mol_file_comparison`.

## What was done

For each of the 250 clean 50/50 molecules:

1. RDKit parses the source SMILES into a molecule.
2. RDKit writes **two real MOL files**:
   - `data/bbbp_mol/source/NNNN.mol` from the source SMILES;
   - `data/bbbp_mol/canonical/NNNN.mol` from its canonical SMILES.
3. Each MOL file is read back with `Chem.MolFromMolBlock`, and the **first ten
   heavy atoms of the MOL atom block are assigned to q0..q9** — the primitive
   "SMILES order" rule, but with a `.mol` as the input structure.
4. The permeability label from the CSV is stored in
   `data/bbbp_mol/labels.csv` alongside both SMILES forms.

The same 12-qubit circuit (Pauling Ry angles, bond-order Rxx, global tail), the
same ten folds and the same classifiers are used for every arm.

## Result: the format changes nothing

| Comparison | Identical features? |
|---|---|
| MOL from source SMILES vs SMILES_ORDER on the source string | **Yes** (hash `7bb43626…` in both) |
| MOL from canonical SMILES vs canonical traversal | **Yes** (hash `a40c530d…` in both) |

`Chem.MolToMolBlock` writes the atoms in the RDKit atom-index order, which is
the order in which the SMILES was parsed, and `MolFromMolBlock` reads them back
in that same order. So a `.mol` generated from a source SMILES carries exactly
the same atom ordering as that string. The primitive arm therefore reproduces
the original score exactly.

| Technique | Acc, C=10 | AUC, C=10 | Acc, nested | AUC, nested |
|---|---:|---:|---:|---:|
| Original SMILES order | 0.748 | **0.836** | 0.770 | **0.842** |
| **MOL files, source atom order** | 0.748 | **0.836** | 0.770 | **0.842** |
| Canonical traversal | 0.657 | 0.723 | 0.646 | 0.717 |
| **MOL files, canonical atom order** | 0.657 | 0.723 | 0.646 | 0.717 |
| NEW chemical coverage + TPSA | 0.686 | 0.754 | 0.689 | 0.778 |
| Classical RF on RDKit descriptors | 0.706 | 0.785 | — | — |

**It does not beat the original: it *is* the original.** The `.mol` container
does not normalize the atom order; the information that mattered was never the
file format but which atom RDKit calls number 0. Writing a `.mol` from the
canonical SMILES does fix the order (and gives the lower, leakage-free 0.723),
but that is simply canonicalization in a different container.

### Is it the `c` vs `C=C` notation?

Not directly. `python -m experiments.run_notation_equivalence_check` rewrites
each molecule in aromatic lowercase and in Kekulé uppercase while keeping the
non-canonical traversal (`tables/notation_equivalence.csv`):

| Check | Fraction of molecules |
|---|---:|
| Aromatic rewrite gives the same features as Kekulé rewrite | **88.4%** |
| Source equals aromatic rewrite | 59.6% |
| Source equals Kekulé rewrite | 57.2% |

RDKit sanitizes both notations to the same aromatic bonds (bond order 1.5), so
the circuit sees the same elements and bond orders — the words `c` and `C=C`
never enter the quantum features. When the two rewrites differ (11.6%), it is
because RDKit's non-canonical writer chose a different *atom traversal*, not
because of the bond notation.

So the precise statement is: the model reads **atom order**, which is a side
effect of how the source string was written. The aromatic/Kekulé flags and the
row number are correlated proxies for the same provenance, but the circuit's
input channel is the atom numbering. A `.mol` preserves that numbering, hence
the identical score.

### Starting at a random atom of the MOL block

`python -m experiments.run_mol_random_start` picks a random heavy atom as q0
and walks the MOL atom block cyclically, with five different seeds
(`tables/mol_random_start_*.csv`, `figures/mol_random_start.png`):

| Arm | Acc, C=10 | AUC, C=10 |
|---|---:|---:|
| Original first atom of the MOL block | 0.748 | **0.836** |
| Random start, mean over 5 seeds | 0.683 | 0.751 |
| Canonical traversal (reference) | 0.657 | 0.723 |

Per-seed AUC ranges from 0.720 to 0.777. Randomizing the starting atom removes
most of the advantage (0.836 → 0.751) but not all: a cyclic rotation still
preserves the *relative* order of the source atoms, so a weaker provenance
signal survives. This is direct evidence that the specific atom numbered 0 is
the main channel used by the primitive encoding.
